# AI时代也必须掌握的设计模式

AI时代，即使Vibe Coding能替代大部分程序员的双手，但是作为决策者，设计模式仍是开发者们不得不品尝的一环。

用一句大白话来概括设计模式：设计模式就是在软件开发过程中，前辈们踩了无数坑后总结出来的“经典的代码套路”。它不是技术语法，而是一种解决方案的模板，就像围棋中的“定式”一样。告诉你在面对特定问题时，使用哪种方式处理最优雅、最容易维护。


作为一个前端开发者，在实际开发中真正高频使用的设计模式也就7-8种，下面我按照一定的优先级给大家一一介绍。

## 观察者模式（Observer）/ 发布-订阅模式（Pub-Sub）
观察者模式是一种行为设计模式，它允许一个对象（主体）维护一组依赖者（观察者），并在状态发生变化时自动通知它们。

这是前端最需要掌握的核心设计模式，没有之一。在前端场景中，Vue的响应式系统、React的useEffect依赖追踪、EventBus事件总线、跨组件通信。这事现代前端框架的基石。

发布订阅模式是一种消息范式，它定义了发布者（Publisher）和订阅者（Subscriber）之间的依赖关系，但两者并不直接通信，而是通过一个中间的事件通道（Event Channel / 消息代理）进行解耦。

两种模式的核心都是定义了一种一对多的依赖关系，当状态变化时可以自动通知多个对象。两者的区别在耦合程度和通信方式


## 单例模式（Singleton）
单例模式是一种创建型设计模式，它确保一个类有且仅有一个实例，并提供一个全局访问点来获取该实例。

适用场景
全局共享资源：如日志记录器、数据库连接池、配置管理器。

全局状态管理：如 Redux/Vuex 的 store、事件总线（Event Bus）。

工具类或缓存：如全局缓存对象、工具函数集合。

避免重复创建开销大的对象：例如 DOM 操作中的弹窗实例

## 工厂模式（Factory）
工厂模式是一种创建型设计模式，它将对象的创建过程封装起来，让客户端（调用者）无需直接使用 new 关键字或具体类的构造函数，而是通过一个工厂对象或工厂方法来获取所需实例。

解耦：客户端只依赖工厂接口，不依赖具体实现类。
集中管理：所有对象创建逻辑集中在工厂中，便于维护和修改。
扩展性：增加新的产品类时，只需扩展工厂，无需修改已有客户端代码（符合开闭原则）。



## 总结（暂定方向）
不知道经过上面的阅读，对设计模式有没有更多的感悟。
其实就在大家在日常开发中已经使用了很多设计模式，只是你不知道这么做的方式叫什么？
经过对设计模式的学习后，以后描述自己的项目、需求、功能点时，不要大白话的描述代码了，而是通过什么设计模式实现了什么功能。
